# song-to-sheet-music

노래 한 곡을 악보로 바꿔 주는 서비스다. 들리는 악기마다 파트보를 하나씩 쓴다 — 드럼, 베이스, 기타(음표 파트와 리듬 차트), 피아노, 그리고 가사가 붙은 노래 선율 — 모든 파트가 하나의 마디 격자·조성·코드 진행을 공유하며, MusicXML·MIDI·PDF 로 나온다. YouTube 링크나 디스크의 녹음 파일을 넣으면 된다.

공개 모델 일곱 개 — 6-스템 분리기, 드럼 피스 분리기, 박 추적기, 전사기 셋, 코드 인식기 — 를 model-compose 로 이어 붙여, 파이프라인 전체를 NVIDIA DGX Spark, RTX 4090, 8 GB MacBook Air M1 에서 돌렸다. 각 기기에서 돌아가는지, 한 곡에 얼마나 걸리는지, 파트보가 출판된 악보에 얼마나 가까운지를 물었다. 그러기 위해 대중가요·록 34곡의 파트보를 상업적으로 출판된 파트 악보와 마디 단위로, 사람의 판정 없이 채점했다. 그 출판 악보들은 귀로 받아 적은 것이라 저마다 오류가 있으므로, 모든 수치는 정확도가 아니라 일치율로 읽어야 한다. 드러머 한 명과 기타리스트 한 명이 파트보 발췌를 읽고 연주자라면 받아들이지 못할 것을 말해 주었고, 그 의견이 3절의 기보 규칙을 만들었다.

![웹 UI 에 곡 파일과 제목을 적고 Run 을 누르면 파트마다 첫 페이지가 돌아오는 장면](docs/images/shared/demo.gif)

데모: RTX 4090 에서 가사까지 GPU 로, 디스크의 녹음을 웹 UI(gradio)로 돌려 파트마다 첫 페이지가 돌아오는 장면. 곡에 걸린 45초는 잘라 냈고 나머지는 실제 속도다.

| 피아노 음표 | [piano-transcription](https://github.com/qiuqiangkong/piano_transcription_inference) (Kong 외) | 165 MB | GPU 또는 CPU |
| 베이스·기타 음표 | [basic-pitch](https://github.com/spotify/basic-pitch) (Spotify), 패키지의 ONNX 모델 | 패키지에 포함 | CPU |
| 노래 음표 | [GAME](https://github.com/openvpi/GAME) small, 노래 전사기 (openvpi), ONNX | 46 MB | CPU |
| 코드 (7화음 포함) | [BTC](https://github.com/jayg996/BTC-ISMIR19), 코드 트랜스포머 (Park 외, ISMIR 2019) | 34 MB | GPU 또는 CPU |
| 가사 | Whisper large-v3-turbo 의 CTranslate2 변환판, faster-whisper 로 실행 | 1.6 GB | CPU (x86 Linux 에서는 GPU) |

조성은 믹스에서 추정하고, 파트보는 music21 로 기보해 Verovio 로 렌더링한다. 모든 가중치는 첫 실행 때 내려받으며, 이 리포지토리에는 하나도 들어 있지 않다.

## 빠른 시작

Python 3.10 이상의 가상 환경(우리는 3.13 을 썼다)에 [model-compose](https://github.com/hanyeol/model-compose) 0.4.117 이상, 그리고 FFmpeg, yt-dlp 용 JavaScript 런타임(Node.js, Deno, Bun 중 하나 — 없으면 일부 YouTube 영상이 HTTP 403 으로 실패한다), PNG 페이지용 Cairo 라이브러리(macOS 는 `brew install cairo`, Debian·Ubuntu 는 `sudo apt install libcairo2`)가 필요하다. GPU 를 강력히 권한다. 3분짜리 곡이 RTX 4090 에서는 1분 남짓, 8 GB M1 에서는 25분 걸린다([2절](#2-내-기기에서-돌아가는가)).

실행할 가상 환경 안에서 [uv](https://docs.astral.sh/uv/) 나 pip 으로 설치한다. 여러 단계가 `PATH` 의 `python` 을 실행하므로 그 환경의 것이어야 한다.

```bash
uv pip install model-compose      # 또는: pip install model-compose
```

이 리포지토리를 클론한다.

```bash
git clone https://github.com/MindrLabs/song-to-sheet-music
cd song-to-sheet-music
```

실행한다:

```bash
DEVICE=cuda model-compose up        # NVIDIA GPU 가 없는 기기에서는 DEVICE 를 빼면 된다
```

첫 시작은 모든 컴포넌트의 패키지 — PyTorch, bs-roformer, music21, Verovio 등, CUDA 라이브러리에 따라 2~8 GB — 를 설치하느라 1분에서 몇 분이 걸린다. 컴포넌트들이 동시에 설치하기 때문에, 새 환경에서는 한 컴포넌트가 다른 컴포넌트가 아직 교체 중인 패키지를 임포트하다가 `ImportError` 나 pip 오류로 첫 시작이 멈출 수 있다. `model-compose up` 을 다시 실행하면 설치는 이미 끝나 있어 몇 초 안에 뜬다. 우리 세 기기 모두 한 번에 뜨지 않았다(표 3). 시작할 때마다 같은 `No module named …` 가 나오면 문제 해결을 본다.

웹 UI 는 `http://localhost:8081`, HTTP API 는 `http://localhost:8080/api` 에 뜬다. `PORT`, `SERVER_PORT`, `DEVICE` 를 바꾸려면 `.env.sample` 을 `.env` 로 복사한다. "Song to Sheet Music" 에 YouTube 링크를 붙여 넣고 곡 제목을 적은 뒤 실행한다. 서비스는 Ctrl+C 로, 또는 이 디렉터리에서 다른 셸을 열어 `model-compose down` 으로 멈춘다.

요청 예:

```bash
curl -X POST http://localhost:8080/api/workflows/runs \
  -H "Content-Type: application/json" \
  -d '{"workflow_id": "full", "input": {"url": "https://youtu.be/<video-id>", "title": "My Song"}}'
```

`url` 대신 `"audio": "/path/to/song.wav"` 를 주면 디스크의 녹음을, FFmpeg 가 읽는 어떤 형식이든 받는다. `"parts": "drums,bass"` 는 그 파트만 쓰고 나머지 파트의 단계는 건너뛴다 — CPU 에서는 25분과 몇 분의 차이다. `up` 이 패키지를 설치한 뒤에는 같은 입력을 명령줄에서도 쓸 수 있다: `model-compose run full --input '{...}'`.

| 첫 실행 때 | 일어나는 일 |
| :---: | --- |
| 가중치 | 약 3.1 GB 가 Hugging Face 와 PyTorch 의 통상 캐시로 내려온다: Whisper 1.6 GB, BS-Roformer-SW 700 MB, DrumSep 438 MB, piano-transcription 165 MB (`~/.cache/models`), Beat This! 77 MB, GAME 46 MB (`~/.cache/game-onnx`), BTC 34 MB (`~/.cache/btc-chords`) |
| 출력 | 모두 `./output` 에 쌓인다: 곡의 FLAC, 스템, `tempo.json`, `key.json`, `chords.json`, 그리고 파트마다 MusicXML·MIDI·PDF·페이지 그림. 한 번에 한 곡이며, 다음 실행이 덮어쓴다 |

MusicXML 은 MuseScore 에서 쓰인 악기 그대로 열린다. 베이스 파트는 베이스 악보답게 적힌 것보다 한 옥타브 아래로 소리 나고, 타브 보표는 타브로 열리며, 드럼 파트는 MuseScore 의 드럼 세트로 열려 타격마다 제 소리가 난다.

사용할 권리가 있는 녹음만 처리하기 바란다.

## 요약

아래의 모든 시간은 기기마다 한 곡을 두 번 돌려 두 번째 실행을 적은 것이고, 모든 일치율은 그 파트를 비교할 수 있었던 곡들의 중앙값이다.

1. 3분짜리 곡이 RTX 4090 에서 가사까지 GPU 로 57초(기본값인 CPU 가사로는 1분 48초), DGX Spark 에서 2.5분, 8 GB M1 MacBook Air 에서 24분 걸리며, 대부분은 스템 분리다([2절](#2-내-기기에서-돌아가는가)).
2. 세 기기가 같은 마디 격자·조성·코드·드럼 타격을 썼다. 음높이 파트는 기기마다 몇 음, 피아노는 스무 음에 하나쯤 다르고, M1 의 가사는 단어의 3분의 1쯤 다르다([2](#2-내-기기에서-돌아가는가)).
3. 34곡의 상업 출판 파트보와 비교해 코드 근음은 곡 길이의 0.80 에서 일치하고, 드럼 킥·스네어는 F-measure 0.94·0.84, 베이스 음표는 재현율 0.76·정밀도 0.78, 노래 선율은 음표의 0.71, 가사는 음절의 0.48 이 일치한다([표 2](#요약)).
4. 기타 파트가 가장 약하다. 스트로크 위주의 디스토션 기타에서 음표 파트는 출판 악보의 리듬 슬래시에 대해 F 0.41 이고, 리듬 차트는 0.93 이다 — 그런 곡은 차트를 읽는다([3.4](#34-기타)).
5. 피아노 파트는 들리는 것을 그대로 쓰기 때문에 출판 건반 악보의 두세 배 음표를 쓴다. 그 악보들에 대한 정확한 음표 재현율은 오른손 0.42, 왼손 0.55 다([3.5](#35-피아노)).
6. 규칙 여섯 개가 날 MIDI 를 연주자가 받아들인 파트보로 바꿨다: 모든 파트에 하나의 마디 격자, 곡의 단락마다 리허설 마크가 붙은 두 성부의 드럼 파트, 스템 자체의 스펙트럼으로 확인한 베이스 옥타브, 스템의 음량이 뛰는 곳에서 나눈 연타, 연주 가능한 타브, 선율 위에 코드·아래에 가사를 둔 리드 시트([3](#3-파트별-결과)).
7. 설치가 거친 부분이다. 첫 `model-compose up` 은 수 GB 의 패키지를 한꺼번에 설치하다 설치 오류로 멈출 수 있고, 그 전에 한 번만 할 단계가 몇 있다. [빠른 시작](#빠른-시작)에 그 단계와 시작이 실패할 때 할 일을 적었다.

## 1 실험 환경

표 3: 기기와 시간 측정 방법

| 기기 | OS, Python | model-compose, torch | 조건 | 첫 시작 |
|---|---|---|---|---|
| MacBook Air M1, 8 GB 통합 | macOS 27, 3.13 | 0.4.117, torch 2.14 (CPU) | 전원 연결, 재부팅 안 함; 편집기·계측을 돌리는 세션·쉬고 있는 다른 model-compose 서비스가 열려 있었다; 실행 중 가용 메모리 평균 1.8 GB | 두 컴포넌트가 동시에 torch 를 설치하다 pip 오류로 두 번 멈춤, 세 번째 시도에서 61초에 기동 |
| RTX 4090 워크스테이션 (24 GB; RAM 61 GB, GPU 2개 중 1개 사용) | Ubuntu 22.04, 3.13 | 0.4.117, torch 2.13 cu126 (575 드라이버에 맞춰 model-compose 가 선택) | 공용 기기; 다른 GPU 에서 다른 사용자의 작업이 돌아 RAM 여유가 2.5 GB 까지 줄었다 | 여섯 번 멈춤: 처음은 torch 를 받는 중에, 그 뒤로는 컴포넌트들이 캐시된 같은 torch 휠을 동시에 풀다 매번 몇 초 만에. torch 만 따로 설치한 뒤(문제 해결) 45초에 기동 |
| DGX Spark (GB10, 120 GB 통합) | Ubuntu 24.04 aarch64, 3.13 | 0.4.117, torch 2.13 cu130 | 공용 기기, 유휴 | pip 오류로 두 번 멈춤, 세 번째 시도에서 4.5분에 기동 (Zenodo 에서 165 MB 피아노 체크포인트를 받는 시간 포함) |

- 모든 실행은 새 가상 환경에서 위의 빠른 시작을 그대로 따랐다. 곡은 Tom McKenzie 의 [Karma](https://zenodo.org/records/19683001) (3:19, AlbumDB 멀티트랙 세트, CC BY 4.0)를 로컬 파일로 넣었다. 기기마다 두 번 돌려 두 번째를 적었고, RTX 4090 은 `LYRICS_DEVICE=cuda` 로 두 번 더 돌렸다. 최대 메모리는 프로세스 트리 전체의 상주 크기를 1초마다 표본한 것이고, RTX 4090 은 GPU 의 사용 중 메모리를 더했다. Spark 의 통합 메모리는 프로세스별로 읽을 수 없다.
- 일치율은 한국과 서양의 대중가요·록 34곡(각 3~6분)을 상업 출판 파트 악보와 비교해 측정했다. 스크립트가 출판 PDF 를 읽어 코드 진행으로 마디를 우리 것과 맞춘 뒤 음표 단위로 비교한다. 출판 악보도 곡도 여기에 포함하지 않았다. 34곡은 DGX Spark 에서 파이프라인을 통과했고, 2절의 세 기기 비교는 같은 코드를 기기마다 돌린 것이다.
- 가중치: `Politrees/UVR_resources` 의 BS-Roformer-SW `model_BandSplit-Roformer_SW_by-jarredou.ckpt` 와 MDX23C DrumSep `MDX23C-DrumSep-aufr33-jarredou.ckpt`; Beat This! `final0`; piano-transcription `CRNN_note_F1=0.9677_pedal_F1=0.9186.pth` (Zenodo 4034264); basic-pitch 0.4.0 의 ONNX 모델; GAME 1.0.3 small ONNX; BTC 커밋 `2682317`; `dropbox-dash/faster-whisper-large-v3-turbo`, int8.
- 판정: 표의 수치에 사람 판정은 없다. 드러머와 기타리스트가 드럼·기타 파트의 발췌를 읽고 어떤 음을 연주하겠는지 답했으며, 그 답은 수치가 아니라 기보 규칙을 바꿨다.

## 2 내 기기에서 돌아가는가

표 4: 단계별 완료 시각, 시작부터의 초 (3분짜리 곡, 두 번째 실행)

| 단계 | RTX 4090 (가사 GPU) | DGX Spark | M1, 8 GB (CPU) |
|---|---|---|---|
| 박과 마디 | 6 | 5 | 15 |
| 조성, 코드 | 17 | 17 | 29 |
| 6 스템 | 24 | 53 | 921 |
| 드럼 피스 | 35 | 73 | 1,438 |
| 베이스 파트 | 39 | 86 | 987 |
| 기타 파트, 리듬 차트 | 34 | 75 | 992 |
| 피아노 파트 | 41 | 89 | 1,268 |
| 가사 붙은 보컬 파트 | 55 | 149 | 1,224 |
| 완료 | 57 | 151 | 1,449 |

- **비용은 분리다.** M1 에서 6-스템 분리기만 15분, 드럼 피스가 9분 더 걸린다. 다른 파트의 전사와 기보는 드럼 피스와 나란히 돈다. RTX 4090 은 곡 전체가 Spark 의 분리와 비슷한 시간에 끝난다.
- **파트는 나란히 돈다.** 스템이 저장되면 다섯 파트가 함께 시작하고, 드럼 피스와 가사가 마지막에 끝난다. `parts` 는 파트를 단계째 건너뛴다. Spark 에서 드럼과 베이스만은 72초, 전 파트는 149초였다.
- **가사는 CPU 에서 돈다.** `LYRICS_DEVICE=cuda` 를 주지 않는 한 그렇다. Whisper 를 돌리는 CTranslate2 에 ARM Linux(Spark)용과 Mac 용 CUDA 빌드가 없기 때문이다. Spark 의 2.5분 중 1분쯤이 그것이다. RTX 4090 에서는 1분 48초와 57초의 차이라, 그곳에서는 켜는 게 좋다.
- **메모리.** M1 은 편집기를 연 상태에서 8 GB 중 3.9 GB 가 최대였다. 브라우저까지 열고 스왑 9 GB 를 쓰던 때는 같은 곡이 40분 걸린 적이 있으니 닫을 수 있는 것은 닫는다. RTX 4090 은 최대 GPU 메모리 6.3 GB 와 RAM 7.1 GB, Spark 는 6.1 GB 를 썼다.
- **첫 시작.** model-compose 는 첫 시작 때 컴포넌트마다 패키지를 한꺼번에 설치하며, CUDA 드라이버에 맞는 torch 빌드를 고른다(RTX 4090 의 575 드라이버에는 cu126, Spark 에는 cu130). 설치가 서로 부딪쳐 세 기기 모두 한 번에 뜨지 않았다. M1 과 Spark 는 세 번째에 떴다. RTX 4090 은 첫 시작이 torch 를 받다 죽은 뒤, 여러 컴포넌트가 캐시된 같은 휠을 동시에 풀면서 매번 몇 초 만에 실패했고, torch 를 한 번 따로 설치하자 끝났다. 가상 환경은 Mac 에서 1.7 GB, CUDA 에서는 6~7.5 GB 가 된다.

표 5: 같은 곡을 세 기기에서 — 결과가 얼마나 일치하는가

| 출력 | 한 기기에서 두 번 | 기기 사이 |
|---|---|---|
| 박, 마디, 조성, 코드 | 동일 | 세 기기 모두 동일 |
| 드럼 파트 | 동일 | 세 기기 모두 2,137 타격; 두 GPU 는 바이트까지 같음 |
| 기타 음표 | 동일 | F 0.998–0.999 (1,929–1,932 음) |
| 베이스 음표 | 동일 | F 0.96–0.97 (423–425 음) |
| 노래 음표 | 동일 | 두 GPU 는 동일; M1 은 어느 쪽과도 F 0.93 |
| 피아노 음표 | 동일 | F 0.95–0.96 (197–207 음) |
| 가사 | 동일 | GPU 사이 단어의 90% 가 같음 (둘 다 CPU Whisper 면 99%); M1 과 어느 쪽 사이든 67–70% |

분리기의 연산은 GPU 와 CPU 사이에 끝자리가 다르고, 전사기의 문턱값이 그것을 여기저기 한 음으로 바꾼다 — 스템이 가장 희미한 피아노에서 가장 많다. Whisper 는 노래 음표가 있는 곳만 들으므로, M1 의 조금 다른 음표가 다른 구간을 듣게 해 가사가 음표보다 더 많이 다르다. 기보 규칙은 결정적이다. 같은 음표가 들어가면 같은 파트보가 나온다.

## 3 파트별 결과

### 3.1 박, 마디, 조성과 코드

모든 파트는 전체 믹스에서 박 추적기가 찾은 강박으로 만든 하나의 마디 격자에 적히므로 파트 사이에 마디 번호가 일치한다. 6/8 곡은 6/8 로 적힌다. 추적기가 한 구간에서 곡의 맥박보다 두 배 빠른 박을 따라가거나 같은 박을 두 번 찾으면, 격자를 놓기 전에 그 박을 반으로 줄이거나 지운다 — 이 수정 하나로 코드 근음이 0.77 에서 0.80 으로 올랐고 적힌 템포가 출판 악보와 맞게 되었다.

조성은 곡마다 한 번 추정하며 모든 음높이 파트가 거기서 조표를 받는다. `key` 로 덮어쓸 수 있다. 코드는 코드 트랜스포머 BTC 가 마디 격자 위에서 낸다. 근음은 곡 길이의 0.80, 장단은 0.76, 7화음은 0.61 에서 출판 악보와 일치한다(29곡). 처음 시도한 크로마 기반 추정기는 BTC 가 0.72·0.56 인 곳에서 0.67·0.50 이었다. 코드에 전위는 없고, 코드를 한 음씩 그리는 리프 위에서는 악보가 코드 하나를 쓰는 곳에 박마다 바뀔 수 있다. 베이스·기타·보컬 파트가 코드 기호를 찍고, 드럼 파트는 거기서 곡의 단락을 읽는다.

### 3.2 드럼

MDX23C DrumSep 이 드럼 스템을 킥, 스네어, 탐, 하이햇, 라이드, 크래시로 나누고, 피스마다의 시작점이 타격이 된다. 멀티트랙의 실제 킥·스네어 트랙에 대해 킥의 87%, 스네어의 100% 를 되찾았으며, 실제 드럼 믹스를 넣어도 분리된 스템을 넣어도 같았다. 출판 드럼 악보(20곡)에 대해 킥·스네어·하이햇은 F 0.94·0.84·0.83, 크래시 0.72, 탐 0.56 이다.

드러머가 요청한 것과 우리가 쓴 것: 손은 기둥을 위로, 킥은 아래로 둔 두 성부의 파트, 음길이와 쉼표는 박에서 나눔; 필인 뒤에 크래시가 오는 곳에 리허설 마크를 두고, 같은 코드를 치는 단락이 같은 글자를 받아 마크가 곡의 형식(A B A B C …)으로 읽히게 함 — 출판 악보의 단락 경계에 F 0.41 로 놓이며, 8마디마다 마크를 두면 0.24 다; 하이햇인지 라이드인지는 어느 피스가 더 크게 울리는지로 몇 마디씩 정함(타격의 0.87 이 악보와 같은 심벌); 그리고 타격 단위의 음량 게이트. 모든 드럼 피스에 다른 피스가 조금씩 섞여 들고 시작점 검출기가 그 번짐에서 "타격" 을 찾기 때문이다. 게이트는 진짜 타격도 잃는다. 스네어보다 훨씬 조용한 탐과 크래시는 번짐으로 여겨져 빠지므로, 탐을 작게 믹스한 곡은 일부를 잃는다.

### 3.3 베이스

basic-pitch 가 베이스 스템을 30–400 Hz 안에서 전사하고, 파트는 분리된 스템에서 전사기가 체계적으로 틀리는 것을 고친다. 옥타브는 스템 자체의 스펙트럼으로 확인한다. 모델이 일부 음에서 한 옥타브 위 배음을 고르기 때문이다. 전사기가 긴 음 하나로 합쳐 버리는 연타는 스템의 음량이 뛰는 곳에서 나눈다. 스템의 음높이가 한 옥타브 위로 미끄러지는 곳에는 슬라이드를 그린다 — 내려가는 슬라이드는 연주자들의 판정에서 맞는 것보다 틀린 것이 많아 올라가는 것만 쓴다. 출판 베이스 악보(25곡)에 대해 음표는 재현율 0.76·정밀도 0.78 로 일치한다.

음표 아래에 타브가 붙는다. 4현이고, 선율이 E 아래로 내려가면 5현(낮은 B)을 쓰며, `tab: false` 로 뺄 수 있다. 운지는 표준 조율에서 연주 가능한 것, 낮은 포지션 우선이고, 녹음의 운지는 아니다.

### 3.4 기타

기타 스템에서 파트 둘이 나온다. 음표 파트는 basic-pitch 를 70–1,400 Hz 에서 베이스와 같은 옥타브·연타 보정과 함께 쓴 초벌이다. 깨끗한 피킹 선율에서는 쓸 만하고, 스트로크 위주의 디스토션 기타에서는 맞는 음을 거의 못 찾는다 — 출판 악보가 리듬 슬래시로 쓴 스트로크에 대해 F 0.41 이다(3곡). 리듬 차트는 기타의 어택에서 읽은 리듬 슬래시 위에 코드 기호를 쓰는데, 출판 악보가 스트로크 구간을 쓰는 방식 그대로이며, 같은 마디에서 0.93 이다. 음표 파트가 빽빽한 곳은 차트를 읽으면 된다. 곡의 모든 기타가 스템 하나에 들어 있어 어느 파트도 리듬과 리드를 가리지 못한다.

타브는 기타리스트가 요청한 대로 손이 짚을 수 있는 운지다. 스트로크 코드는 곡의 코드의 표준 모양으로, 그 포지션에서 손이 닿는 범위로(프렛은 위로 갈수록 좁아진다), 낮은 포지션 우선이다. 녹음의 운지는 아니다. 같은 음에 출판 타브와 다른 줄을 고른 경우(6곡 2,242음의 59%) 대개 더 높은 포지션에서 친다. 낮은 E 아래의 음 — 드롭 D 곡 — 은 타브에서 빠지고, 반음 내린 곡은 프렛이 하나 낮게 나온다.

### 3.5 피아노

piano-transcription 이 피아노 스템을 큰보표에 쓴다. 출판 건반 악보가 쓰는 것보다 많이 듣는다. 두세 배의 음표인데, 출판 악보는 편곡하고 전사기는 하지 않기 때문이다. 출판 건반 악보에 대한 정확한 음표 재현율은 오른손 0.42, 왼손 0.55 다(15곡과 14곡). `min_pitch`(기본 MIDI 36) 아래 음은 피아노 스템에 새어 든 베이스로 보아 버린다. 여섯 스템 중 분리기가 가장 못 건지는 것이 피아노다. 멀티트랙의 실제 피아노 트랙에 대해 BS-Roformer-SW 는 피아노의 41% 를 피아노 스템에 넣었고, Demucs htdemucs_6s 는 5% 였다.

### 3.6 보컬과 가사

model-compose 의 전사기는 악기용이다. 보컬 스템에서 basic-pitch 는 출판 선율과 음표의 절반쯤 일치했고, 노래 전사기 GAME 은 0.69 였다(6곡). 그래서 GAME 이 노래 음표를 쓴다. 보컬 파트는 리드 시트다 — 선율 위에 코드 기호, 아래에 가사를 음표마다 한 음절씩 붙이고, 낮은(남성) 선율은 8 이 붙은 높은음자리표에 쓴다. 출판 선율(27곡)에 대해 음표는 옥타브를 무시하고 0.71 에서 일치한다. 백 보컬이 스템을 공유해 선율에 끼어들 수 있고, 외치거나 거친 노래는 전사가 나쁘다.

가사는 Whisper 가 노래 음표가 있는 곳만 들어서 낸다. 스템 전체를 들려주면 밴드만 연주하는 곳에서 글을 지어냈고 자체 음성 검출기가 록 보컬을 버렸는데, 노래 구간만 들려주면 인쇄된 가사의 0.74 를 들었다(7곡, 최저 0.60). 스템 전체는 0.61 이었다. 각 음절은 가장 가까운 음표로 간다. 출판 악보 음절의 0.48 이 악보가 붙인 음표에 놓이며, 선율의 음이 어긋난 곳 — 잘못 들은 단어, 한 음 이르거나 늦은 음절, 부른 것보다 적은 음을 찾아 한 음에 두세 음절 — 에서는 그보다 적다. `lyrics_language` 는 Whisper 에 언어를 알려 준다. 없으면 스스로 알아낸다.

## 4 권고

- **하드웨어:** RTX 4090 은 가사까지 GPU 로 한 곡을 1분 남짓에 끝내고 GPU 메모리 최대 6.3 GB 를 썼으니 8 GB 이상의 GPU 면 들어갈 것이다. 우리는 4090 과 DGX Spark(2분 30초)만 측정했다. 8 GB Mac 은 CPU 로 25분쯤에 끝낸다. RAM 8 GB 아래는 시도하지 않았다.
- **CPU 에서는 필요한 파트만 요청한다:** `"parts": "bass"` 는 드럼 피스 분리, 피아노·보컬 전사기, 가사를 건너뛰어 전 파트 25분 대신 몇 분에 끝난다.
- **가사를 GPU 로:** NVIDIA GPU 가 있는 x86 Linux 에서는 `LYRICS_DEVICE=cuda` 를 준다 — RTX 4090 에서 시간이 절반이 됐다. Spark 나 Mac 에서는 그대로 둔다. CTranslate2 에 그쪽 CUDA 빌드가 없다.
- **디스크의 녹음**은 `url` 대신 `audio` 로 넣는다. 더 빠르고 JavaScript 런타임이 필요 없으며, 온라인에 없는 곡을 넣는 유일한 길이다.
- **드럼·베이스·보컬 파트를 먼저 읽는다.** 출판 악보와 가장 잘 맞는다. 스트로크 곡에서는 기타 음표 파트보다 리듬 차트를 택하고, 피아노 파트는 덜어 내야 한다고 생각하면 된다.
- **조성을 지정한다.** 곡이 두 조성 사이에 걸칠 때다. `key.json` 에 `low_confidence` 가 적히고, 틀린 조표는 맞는 파트보도 읽기 어렵게 만든다.
- **빽빽한 곡**은 `"grid": 2` 가 읽기 좋다. 16분음표 대신 8분음표 리듬으로 쓴다.
- **MuseScore 에서 고친다.** MusicXML 은 맞는 악기로, 타브와 드럼 세트까지 열린다. 몇 개 틀린 음은 전사기가 고쳐 주길 기대하지 말고 거기서 고친다.
- **Ctrl+C 로 멈춘다.** `model-compose run` 은 아무것도 설치하지 않는다. 먼저 `model-compose up` 을 한 번 돌리고, 첫 시작이 죽으면 다시 돌린다.

## 5 한계와 측정하지 않은 것

- **곡마다 박자 하나.** 4/4, 3/4, 6/8 은 인식한다(12/8 도 같은 규칙으로, 미검증). 곡 중간의 박자 변화는 인식하지 못하고, 추적기가 박을 잘못 읽은 곡은 모든 곳에서 격자가 틀린다.
- **출판 악보는 참고일 뿐 정답이 아니다.** 출판사가 귀로 받아 적은 것이라 곳곳에서 녹음과 다르다. 우리 것과 다른 곳에서 누가 맞는지 들어서 가리지 않았다. 연주자들이 읽은 발췌만 예외다.
- **기타 수치는 3곡**이다. 스트로크를 슬래시로 쓴 출판 악보가 드물기 때문이고, 다른 기타 수치는 6곡이다. 가사는 영어나 한국어 가사가 있는 27곡에서 채점했다.
- **리듬 섹션만.** 스트링, 관악기, 신스, 두 번째 기타는 "other" 스템으로 들어가 적히지 않는다. 피아노나 베이스가 없는 곡은 파트 대신 `piano.skipped.txt` 를 받는다.
- **드럼:** 오픈 하이햇은 닫힌 것처럼 적힌다(오픈 타격 열넷에 하나쯤은 라이드로 나온다). 키트의 랙 탐 둘이 한 줄을 쓴다. 다른 악기가 드럼 피스에 번져 든 타격이 가끔 적히고, 조용한 탐이 가끔 빠진다.
- **타브**는 연주 가능한 운지이지 녹음의 운지가 아니고, 드롭 D 나 반음 내린 조율을 모른다.
- **기기 간 재현성**은 표 5 와 같다. 음높이 파트는 기기 사이에 몇 음, 피아노는 스무 음에 하나, 가사는 단어의 3분의 1까지 다를 수 있다.
- **측정하지 않은 것:** 대중가요·록 이외의 장르, 기악곡, 6분 넘는 곡, 24 GB 보다 작은 GPU, Apple 의 GPU(MPS; Mac 에서 분리기는 CPU 로 돌았다), 느린 회선에서의 첫 실행 다운로드 시간, 그리고 3절의 두 비교 이외에 분리기·전사기가 대안들과 어떻게 비교되는지.

## 참고

### `full` 의 입력

| 입력 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| `url` | string | `url`, `audio` 중 하나 | - | YouTube (또는 yt-dlp 가 지원하는) URL |
| `audio` | string | `url`, `audio` 중 하나 | - | 디스크의 녹음 경로, FFmpeg 가 읽는 어떤 형식이든 |
| `parts` | string | 아니오 | `all` | 쓸 파트: `all`, 또는 `drums`, `bass`, `guitar`, `piano`, `vocals` 의 쉼표 목록. 없는 파트는 단계째 건너뛴다 |
| `title` | string | 아니오 | - | 모든 파트의 머리에 붙는다 ("My Song — Bass") |
| `key` | string | 아니오 | 추정 | 조성, 예: `"C minor"`, `"Ab"` |
| `grid` | integer | 아니오 | `4` | 리듬을 맞추는 4분음표당 분할 수; `4` = 16분, `2` = 8분 |
| `tab` | boolean | 아니오 | `true` | 기타·베이스 파트 아래의 타브 |
| `language` | string | 아니오 | - | GAME 에 알려 줄 노래의 언어: `en`, `ja`, `yue`, `zh`. 영어 곡에서는 측정 가능한 차이가 없었고, 다른 언어도 없이 된다 |
| `vocal_model` | string | 아니오 | `small` | GAME 크기, `small`, `medium`, `large`. 큰 것이 출판 선율과 더 잘 맞지 않았고 몇 배 느리다 |
| `lyrics_language` | string | 아니오 | - | Whisper 에 알려 줄 가사의 언어 (`ko`, `en`, …). 없으면 스스로 알아낸다 |
| `bpm` | string | 아니오 | `auto` | 피아노 파트: `auto` 는 마디 격자를 따르고, 숫자는 템포 하나로 고정한다 |
| `min_pitch` | integer | 아니오 | `36` | 피아노 파트: 이 MIDI 음높이 아래는 베이스 누출로 보아 버린다 |

결과에는 `key`, `chords` 와 파트마다 `score`(MusicXML 경로, 템포, 박자, 마디 수)와 `render`(PDF 와 페이지 그림)가 있다 — 곡에 해당 악기가 없는 파트는 `skipped` 와 이유, 요청하지 않은 파트는 `null` 이다. `vocals` 에는 `notes` 와 `lyrics` 도 들어 있다.

### 워크플로우

`full` 은 곡 전체 단계를 돌린 뒤 파트마다 워크플로우 하나를 돌린다. 모든 단계는 그 자체로도 워크플로우이고 같은 `./output` 을 읽고 쓰므로, 앞 단계 없이 한 단계만 다시 돌릴 수 있다 — 예컨대 제목을 바꾸고 `engrave-bass` 만 다시 돌린다.

| 워크플로우 | 하는 일 |
|---|---|
| `full` | 전부: 소스, 박, 조성, 코드, 스템, 그리고 요청한 파트 |
| `part-drums`, `part-bass`, `part-guitar`, `part-piano`, `part-vocals` | 저장된 스템에서 파트 하나를 끝까지 |
| `download` | URL 의 오디오를 `./output` 으로 |
| `beats`, `key`, `chords` | 저장된 곡에서 `tempo.json`, `key.json`, `chords.json` |
| `separate`, `split-drums` | 6 스템; 드럼 피스 |
| `transcribe`, `transcribe-bass`, `transcribe-guitar`, `transcribe-vocals`, `transcribe-lyrics` | 스템 하나의 음표; 보컬 음표 위의 가사 |
| `engrave`, `engrave-drums`, `engrave-bass`, `engrave-guitar`, `engrave-guitar-rhythm`, `engrave-vocals` | 저장된 음표에서 파트보를, PDF 와 PNG 로 렌더링 |

환경 변수, 또는 `model-compose.yml` 옆의 `.env` (`.env.sample` 참고):

| 변수 | 기본값 | 설명 |
|---|---|---|
| `DEVICE` | `cpu` | NVIDIA GPU 에서는 `cuda`, 분리기와 전사기용 |
| `LYRICS_DEVICE` | `cpu` | `cuda` 는 CTranslate2 에 CUDA 빌드가 있는 곳(x86 Linux)에서 Whisper 를 GPU 로 돌린다 |

### 문제 해결

- **`FileNotFoundError: 'python'`** — `model-compose up` 을 시작할 때 가상 환경이 활성화돼 있지 않았다.
- **`model-compose run` 에서 `No module named 'torch'`** — 먼저 `model-compose up` 을 한 번 돌린다. `run` 은 패키지를 설치하지 않는다.
- **첫 `up` 에서 `ImportError` 나 pip 오류** — `model-compose up` 을 다시 돌린다. 컴포넌트들이 동시에 패키지를 설치하고 있었다. 시작할 때마다 같은 `No module named …` 가 나오면 설치가 부딪쳐 패키지 하나가 반쯤 깔린 채 남았고 pip 는 그것을 설치된 것으로 본다. 그 패키지만 다시 설치한다. 예: `pip install --force-reinstall --no-deps numba`.
- **시작할 때마다 몇 초 만에 `pip install … torch …` 에서 멈춤** — 컴포넌트들이 캐시된 같은 torch 휠을 동시에 풀고 있었다. 오류에 나온 pip 명령을 직접 한 번 돌린 뒤 다시 시작한다.
- **`/tmp/gradio` 아래 `PermissionError`** — 공용 기기에서 다른 사용자의 웹 UI 가 그 폴더를 갖고 있다. `GRADIO_TEMP_DIR` 을 자기 폴더로 지정한다.
- **다운로드 중 HTTP 403** — Node.js(또는 Deno, Bun)를 설치한다. yt-dlp 가 `PATH` 에서 찾는다.
- **제목 자리에 네모** — 제목의 글자(한국어, 일본어, 중국어)가 든 글꼴을 설치한다.
- **피아노가 있는 곡에 `piano.skipped.txt`** — 스템이 전사하기에 너무 희미했다. 분리기는 피아노의 절반도 못 건진다.
